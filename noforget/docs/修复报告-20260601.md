## 🔴 P0 严重问题（5/5 已修复）

### #1 纪念日混用姨妈模板ID

| 项目 | 内容 |
|------|------|
| **文件** | `cloud/send-reminder/index.js` + `config/constant.js` |
| **问题** | 倒计时提醒的循环中直接硬编码使用了姨妈模板ID `L6aIoXgdKCQpd6wuR1VGYLzQLDZq6SsLlqDdffI8s7w`，与 `sendCountdownReminder()` 函数的逻辑不对应。同时 `sendCountdownReminder()` 内部 `COUNTDOWN_TEMPLATE_ID` 为空字符串，导致无论如何都会走错误的模板 |
| **修复** | ① `config/constant.js`: 增加 `COUNTDOWN: ''` 预留位 ② `send-reminder`: 移除底部的硬编码发送逻辑，改用 `sendCountdownReminder()` 统一处理 ③ 当 `TEMPLATES.COUNTDOWN` 为空时，跳过纪念日提醒并记录日志，不再使用姨妈模板 |
| **风险** | 无 — COUNTDOWN模板ID为空字符串时静默跳过，站长在微信后台配置后填入即可生效 |

### #2 openid字段名不统一

| 项目 | 内容 |
|------|------|
| **文件** | `cloud/send-reminder/index.js` |
| **问题** | `periodData` 集合使用自定义 `openid` 字段（cloud function写入），`countdownItems` 使用微信自动的 `_openid` 字段。`send-reminder` 查询 `periodData` 时只查了 `openid`，未兼容 `_openid` |
| **修复** | ① 查询时 `.field({openid: true, _openid: true, ...})` 同时获取两个字段 ② 新增 `getUserId(user)` 函数：`return user.openid || user._openid || null` |
| **风险** | 低 — 额外多查一个字段无性能影响 |

### #3 periodCloud.js 无重试机制

| 项目 | 内容 |
|------|------|
| **文件** | `utils/periodCloud.js` — `callCloud()` |
| **问题** | 云函数调用失败后直接返回 `{success: false}`，无重试逻辑。冷启动或网络抖动时用户体验割裂 |
| **修复** | 增加指数退避重试（最多3次）：第1次失败后等1s，第2次等2s，第3次等3s。每次重试都打印 warn 日志 |
| **风险** | 低 — 重试机制有 `Math.min(retries, 3)` 兜底，不会无限重试 |

### #4 banner 选中 period 虚拟条目

| 项目 | 内容 |
|------|------|
| **文件** | `pages/index/index.js` — `_initDailyBanner()` |
| **问题** | `_initDailyBanner()` 直接从 `this._rawItems[0]` 取第一个条目，当用户只有 period 类型的条目时，banner 会尝试用 period 数据生成文案（period 没有 targetDate，会生成无意义的banner提示） |
| **修复** | 改用 `this._rawItems.find(item => item.categoryId !== 'period')` 取第一个非 period 条目，仅当全部都是 period 时才回退到 `_rawItems[0]` |
| **风险** | 无 — 仅是查找逻辑的调整 |

### #5 分页问题

| 项目 | 内容 |
|------|------|
| **文件** | `cloud/send-reminder/index.js` — `listCountdownItems()` |
| **问题** | 原函数 `.limit(500)` 最多返500条，且没有分页循环。当用户数超过500时，纪念日提醒会漏掉后面的用户 |
| **修复** | 重写为 `listAllCountdownItems()`：按100条/批分页循环查询，直到取完所有数据 |
| **风险** | 无 — 只影响定时任务，不涉及用户交互 |
