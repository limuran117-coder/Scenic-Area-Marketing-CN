## 二、逐项评估

### 2.1 纯JSON文件（现状）

**现状数据：**
- `wiki/技术配置/Ontology架构设计/data/` 中有 9 个 JSON 文件（metric_snapshots + content_assets）
- 每个 adapter 直接写 JSON 到 `data/` 目录

**优点：**
- Git 可追溯（每次 commit 记录变更）
- 无任何外部依赖
- LLM 直接可读（prompt 中直接塞 JSON）
- 零运维

**缺点：**
- ❌ 无索引，查询全表扫描（1000行就开始慢）
- ❌ 无聚合能力（排名/趋势/环比需加载全部数据到内存）
- ❌ Link Types 实例化困难（双向引用同步维护成本高）
- ❌ 并发写入冲突（多个 adapter 同时写同一文件）
- ❌ 无审计日志（谁在何时写了什么）
- ❌ 随着数据增长，JSON 文件会越来越大（单文件 > 1MB 后难以管理）

**结论：⚠️ 保留用于 Git 快照，不足支撑日常查询**

---

### 2.2 SQLite（本方案选定）

**设计依据：** 本地接入方案.md §2.1 已完成详细设计

**现状：**
- `.profile/ontology/` 目录尚不存在（未实施）
- 但 `本地接入方案.md` 中的 SQLite Schema 已完整设计
- adapter-douyin/xiaohongshu/visitors 三个 adapter 已就位但仍写 JSON

**优点：**
- ✅ **零配置**：Python 内置，无需安装任何服务
- ✅ **SQL 查询**：索引 + JOIN + GROUP BY，秒级聚合
- ✅ **JSON 字段**：SQLite 3.38+ 原生支持 JSON _extract，Link Types 可存 JSON 列
- ✅ **轻量**：单文件 `.db`，无外部进程
- ✅ **原子写入**：事务保证 adapter 并发写入安全
- ✅ **审计日志**：`ingest_log` + `action_log` 内置
- ✅ **与 Python 原生集成**：`sqlite3` 模块无需额外包
- ✅ **数据量足够**：按当前增长估算，1年数据 < 50MB，完全在 SQLite 舒适区
- ✅ **已有完整 Schema 设计**：本地接入方案.md §2.3 的 8 张表设计可直接使用

**缺点：**
- ⚠️ 图关系查询不如 Neo4j（原生的路径查询够用，我们不是社交网络）
- ⚠️ 多人并发写入（当前是单机 agent，不存在）
- ⚠️ 跨语言调用（Python 为主，其他语言需写 bindings — 当前不考虑）

**结论：✅ 选定。本周应启动 SQLite store 实施。**

---

### 2.3 Neo4j

**评估结论：❌ 暂不采用**

**原因：**
1. **需独立服务进程**：Neo4j 需要 Java 运行时 + Docker 容器 + 7474/7687 端口，占用 Mac mini 不必要的资源
2. **学习曲线**：Cypher 查询语言与团队现有 SQL 技能不匹配
3. **数据量不符**：我们全年数据预计 < 50MB，Neo4j 的图查询优势在如此小数据集上体现不出
4. **运维成本**：需要定期备份 Docker volume、监控容器健康，而 SQLite 只是个文件
5. **与现有架构集成成本高**：adapter 需重写，Query Layer 需从 SQL 切换到 Cypher

**未来触发条件（何时值得迁移）：**
- 当 Link Types 的**路径查询**成为主要瓶颈（如：查询"所有与电影小镇竞品相关的竞品的内容资产"这类多跳查询）
- 当数据量超过 **500MB**（约 3-5 年的景区数据）
- 当团队引入需要图数据库的其他应用

### 2.4 OWL/RDF 语义网标准（补充评估）

**与轻量 Agent 系统的适用性：**

| 标准 | 表达能力 | Agent 可读性 | 工具链成熟度 | 结论 |
|------|---------|-------------|------------|------|
| **OWL 2** | 完整语义（传递闭包、等价类） | ❌ LLM 无法直接理解 DL 语法 | 需 Protege/RDFlib | 过度设计 |
| **RDF** | 三元组模型 | ⚠️ 可读但需额外 prompt 注入 | 成熟 | 偏学术 |
| **JSON-LD** | 带 @context 的 JSON | ✅ LLM 原生理解 | 成熟（w3c spec） | ⏳ 未来可考虑 |
| **SPARQL** | 图查询协议 | ⚠️ 需翻译层 | 成熟 | 偏学术 |

**我们的决策（D-001 确认）：**
- 当前：**纯 JSON Schema**（ontology.json）已足够
- Phase 4 之后：如需跨系统互操作（如对接外部数据API），添加 JSON-LD `@context` 使我们的对象可被标准工具引用
- **永远不引入 OWL/RDF/SPARQL**：语义推理能力在我们场景下不是必要项，引入只会增加复杂度

**JSON-LD 轻量采用方案（未来参考）：**
```json
{
  "@context": {
    "ontology": "https://movietown.cn/ontology/",
    "xsd": "http://www.w3.org/2001/XMLSchema#"
  },
  "@type": "ontology:MetricSnapshot",
  "ontology:scenicSpotId": { "@id": "ontology:ScenicSpot/movie_town" },
  "ontology:value": { "@value": 876543, "@type": "xsd:integer" }
}
```

## 四、关键设计决策记录

### D-005：采用 SQLite 而非 Neo4j 作为核心存储
**决策：** SQLite 作为 Ontology Layer 的核心存储引擎。
**理由：**
1. 零配置，Python 内置，与现有 adapter 集成成本最低
2. 已有的完整 Schema 设计（本地接入方案.md §2.3）可直接实施
3. 当前数据量（< 50MB/年）完全在 SQLite 性能舒适区
4. 图查询优势（Neo4j）在小数据集上不值得额外运维成本
5. SQL 技能在团队内可迁移，Cypher 需要额外学习
**触发升级条件：** 数据量 > 500MB 或多跳路径查询成为主要瓶颈。
**参考：Wiki/技术配置/Ontology架构设计/基础设施评估.md

### D-006：JSON 文件作为 Git 快照层保留
**决策：** adapter 同时写 SQLite（查询用）和 JSON（Git 追踪用）。
**理由：**
1. Git 快照提供数据变更历史追溯（谁在哪天改了哪个景区数据）
2. JSON 文件是 adapter 的自然输出格式，改造成本低
3. SQLite 文件本身不进入 Git（`.gitignore`），避免二进制文件膨胀
**实施方式：**
```python
# adapter 输出模式
def persist(data):
    write_to_sqlite(data)       # 核心存储（不 Git）
    write_json_snapshot(data)  # Git 快照（提交到版本历史）
```
