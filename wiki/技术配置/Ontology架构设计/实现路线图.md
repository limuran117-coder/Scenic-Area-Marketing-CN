## 三、关键设计决策记录

### D-001: JSON 而非 OWL/RDF
**决策：** 使用纯 JSON schema，不用 OWL 2 / RDF / SPARQL。
**理由：** 我们的数据量级不需要语义推理引擎。JSON 在 Agent 的 prompt context 中更易被 LLM 理解。未来如果需求升级，可以从 JSON 自动生成 OWL。
**代价：** 没有标准的推理能力（如传递闭包：A→B, B→C → A→C 需要手动实现）。

### D-005: SQLite 而非 Neo4j 作为核心存储
**决策：** SQLite 作为 Ontology Layer 核心存储引擎。
**理由：** 零配置（Python 内置）+ 性能足够（< 50MB/年数据）+ 完整 Schema 已设计（本地接入方案.md）+ SQL 技能可迁移。
**触发升级条件：** 数据量 > 500MB 或多跳路径查询成为主要瓶颈。
**参考：** 基础设施评估.md

### D-006: JSON 文件作为 Git 快照层
**决策：** adapter 同时写 SQLite（查询用）和 JSON（Git 快照用）。
**理由：** Git 快照追溯数据变更历史；adapter 自然输出 JSON，改造成本低；SQLite 文件不进 Git（.gitignore）。
**实施：** adapter 双写模式 — `persist()` 同时调用 `write_to_sqlite()` + `write_json_snapshot()`。

### D-002: wiki 目录作为 Ontology Store
**决策：** Object Types 对应 wiki 子目录，每个 JSON 对象作为 markdown 文件。
**理由：** 零基础设施启动，Git 可追溯，与当前工作流一致。
**当文件 > 1000 时：** 迁移到 SQLite 或 Neo4j。

### D-003: Actions 从 cron 任务中解耦
**决策：** Actions 不直接嵌入 cron 代码，通过 Action Request/Response 模式调度。
**理由：** 审计、回滚、限流统一管控。
**过渡策略：** 先拦截 `send_feishu_card.py` 调用，记录到 Action Log，再逐步接管。
