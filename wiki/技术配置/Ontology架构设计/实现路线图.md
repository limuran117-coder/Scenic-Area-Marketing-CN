## 三、关键设计决策记录

### D-001: JSON 而非 OWL/RDF
**决策：** 使用纯 JSON schema，不用 OWL 2 / RDF / SPARQL。
**理由：** 我们的数据量级不需要语义推理引擎。JSON 在 Agent 的 prompt context 中更易被 LLM 理解。未来如果需求升级，可以从 JSON 自动生成 OWL。
**代价：** 没有标准的推理能力（如传递闭包：A→B, B→C → A→C 需要手动实现）。

### D-005: SQLite 而非 Neo4j 作为核心存储
**决策：** SQLite 作为 Ontology Layer 核心存储引擎。
**理由：** 零配置（Python 内置）+ 性能足够（< 50MB/年数据）+ 完整 Schema 已设计（本地接入方案.md）+ SQL 技能可迁移。
**触发升级条件：** 数据量 > 500MB 或多跳路径查询成为主要瓶颈。
**参考：** 基础设施评估.md

### D-006: JSON 文件作为 Git 快照层
**决策：** adapter 同时写 SQLite（查询用）和 JSON（Git 快照用）。
**理由：** Git 快照追溯数据变更历史；adapter 自然输出 JSON，改造成本低；SQLite 文件不进 Git（.gitignore）。
**实施：** adapter 双写模式 — `persist()` 同时调用 `write_to_sqlite()` + `write_json_snapshot()`。

### D-002: wiki 目录作为 Ontology Store
**决策：** Object Types 对应 wiki 子目录，每个 JSON 对象作为 markdown 文件。
**理由：** 零基础设施启动，Git 可追溯，与当前工作流一致。
**当文件 > 1000 时：** 迁移到 SQLite 或 Neo4j。

### D-003: Actions 从 cron 任务中解耦
**决策：** Actions 不直接嵌入 cron 代码，通过 Action Request/Response 模式调度。
**理由：** 审计、回滚、限流统一管控。
**过渡策略：** 先拦截 `send_feishu_card.py` 调用，记录到 Action Log，再逐步接管。
**Week 2 演进：** D-003 升级为 D-017（5 层治理）+ D-018（Function-backed Action）+ D-019（3 档 category）。详见 `Week2_Actions_Functions.md` §十二。

### D-016: Function 4 类型分类（Pure/SideEffect/FunctionBacked/Aggregator）
**决策：** 引入类型标签区分 4 种 Function，让 governance 可分级。
**理由：** SideEffect Function 必须经 Action 调用，不可被 Agent 直接 invoke；FunctionBacked 是现代 Palantir 主推模式。
**实施：** v1.3.0 §functionTaxonomy；详见 `Week2_Actions_Functions.md` §十二。

### D-017: Action 5 层治理（Submission→Validation→Notification→Audit→Rollback）
**决策：** 所有 Action 必须经 5 层治理链。
**理由：** Palantir Action Type 业界标准，确保"所有写操作可追溯、可回滚"。
**实施：** v1.3.0 §actionGovernance；scripts/ontology/validate.py V-007~V-010 强制校验。

### D-018: Function-backed Action 模式
**决策：** Action 显式声明 functionBacked + functionImpl，调 N 个 Function 组合业务逻辑。
**理由：** 现代 Palantir 主推做法：Action 治理层 + Function 业务逻辑层组合，更易测、复用、OSDK 友好。
**实施：** v1.3.0 actions.*.functionBacked/functionImpl；Week 3+ scripts/actions/ 拆分为 function_impl.py + action_wrapper.py。

### D-019: Action Category 3 档（lowStakes/mediumStakes/highStakes）
**决策：** Action 按风险/成本分 3 档。
**理由：** 不同 Action 治理需求差异巨大；category 让 cron 任务设计时显式选择风险等级。
**实施：** v1.3.0 actions.*.category；governance 字段（requiresApproval/rateLimit/preCondition）按 category 默认填充。

### D-020: V-007~V-010 业务规则层验证
**决策：** 在 V-001~V-006 Schema 验证之上加 4 条 Action 业务规则。
**理由：** Schema 验证保 ontology 一致性，Action 业务规则保业务正确性（状态机前置/审批/可追溯）。
**实施：** v1.3.0 validation.rules V-007~V-010；Week 3 scripts/ontology/validate.py 升级。
