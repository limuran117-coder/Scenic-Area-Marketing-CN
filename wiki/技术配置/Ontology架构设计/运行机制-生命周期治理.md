# Ontology 系统运行机制（生命周期治理）

> 版本：0.1.0 | 日期：2026-08-10 | 关联：ADR-001
> 目标：让 ontology 成为**活系统**——明确何时更新/产出/优化，避免再次"停滞18天"。

---

## 一、核心原则

Ontology 不是一次性建完的静态库，而是**随日常运营持续生长的活图谱**。数据源是现有采集流水（抖音指数/小红书/舆情/竞品），ontology 是这些流水之上的**结构化关系层**。

## 二、何时更新（写入图谱）

| 触发 | 动作 | 负责 |
|------|------|------|
| **每次采集任务完成** | 新 MetricSnapshot/ContentAsset 写入图谱 | 各采集 cron |
| **每日 22:00 复盘** | 当日关键结论写入图谱（如"8/5客群结构转折"） | 复盘任务 |
| **每次竞品周报** | 新增/更新 competes_with、竞品动态结论 | 周度竞争格局 cron |
| **每次日常对话产出新事实** | 站长确认后写入（"movie_town 易主中信资本"类） | 主会话 |
| **每周日** | ontology_daily_work 汇总本周增量 + 校验 | 周日任务 |

**更新一致性铁律**：
- entity ID 一律用业务 ID 单源（`scripts/ontology_constants.py` 的 SCENIC_SPOT_MAP）
- 写前先查重（幂等），不产生重复实体/关系
- 每次写入后跑 `validate_graph`（schema 校验），报错即修

## 三、何时产出（读图谱 → 对外价值）

| 场景 | 产出 | 触发方式 |
|------|------|----------|
| **竞品分析** | "电影小镇的全部竞品 + 各自近期指标对比" | 竞品周报/日报时查询 |
| **趋势洞察** | "某景区 search_index 近 N 天走势 + 是否异常" | 洞察驱动任务查询 |
| **客群分析** | "谁在 target 年轻的女性客群" | 投放策略分析 |
| **战略问答** | "我们在竞争格局中的位置" | 站长对话直接问 |
| **知识图谱可视化** | 导出图谱供人工审视 | 按需 |

**产出标准**：洞察驱动，先给判断、再给数据佐证（沿用 MEMORY 铁律），不是罗列数字。

## 四、何时优化（重构/治理）

| 触发 | 动作 |
|------|------|
| validate 报错 > 3 次 | 检查 schema 定义是否过严/数据是否脏 |
| 图谱实体 > 500 或关系 > 2000 | 审视是否需要归档旧快照（保留近90天） |
| 某关系长期零产出价值 | 评估是否移除该 relation 类型 |
| LLM 查询准确率 < 80% | 优化 Translator 词表 / 关系命名 |
| 新数据源上线 | 评估是否新增 type/relation |

**优化频率**：每月例行审视一次（可并入每周日 ontology 工作），重大重构走 ADR 追加修订。

## 五、健康检查（防停滞）

**每周日 ontology_daily_work 强制自检**（输出四段 ≤200字）：
1. 最近写入时间（>7天无写入 = 告警，防止再停滞18天）
2. 实体/关系增长率
3. validate 通过率
4. 本周新增的结论/关系列表

**告警规则**：若连续 2 周无写入且无产出 → 向站长报告"ontology 停滞"，由站长决定是否挂起（而非默默浪费资源）。
