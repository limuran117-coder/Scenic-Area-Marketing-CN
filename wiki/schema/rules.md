## 目录结构

wiki 按**四类职责**组织（16 个顶层目录）：

| 类别 | 目录 | 内容 |
|------|------|------|
| 📕 业务档案 | `电影小镇/` `复盘报告/` | 本项目全档案（含历史数据/运营规划/演出节目等子目录）|
| 📗 外部情报 | `竞品分析/` `全国景区案例库/` `行业知识/` | 竞品、案例、行业结论（结论索引/动态追踪/景区类型）|
| 📘 知识层 | `concepts/` `entities/` `sources/` `queries/` | karpathy 模式：概念/实体/来源/问答 |
| 📙 规范系统 | `SOP/` `技术配置/` `系统/` `schema/` | 操作规范、技术配置、系统运维、编写规范 |
| 🗄 支撑 | `图表/` `raw/` `archived/` | 图表源文件、未消化原文、归档 |

> 完整逻辑与重组历史见 `wiki/系统/目录结构说明.md`。

## 目录治理规则（2026-09-12 起）

### R1. 目录必须有索引
新建任何目录时，**必须同时创建 `index.md`**，包含：标题、用途说明、文件表（或子目录表）。
无索引的目录视为未完成；`wiki/index.md` 为全库总索引。

### R2. 保护任务写入区
以下目录是 cron 任务的读写目标，**禁止移动/重命名其中文件**：

| 目录 | 使用任务 |
|------|----------|
| `wiki/全国景区案例库/` | 案例库更新 · 爆款公式库更新 · 竞品爆款拆解 · 文旅营销案例 |
| `wiki/行业知识/结论索引/` + `结论索引.md` | 13 个洞察类任务 |
| `wiki/电影小镇/历史数据/` | 周二客流深度报告 · 周度客流洞察 · 月度复盘 |
| `wiki/SOP/竞品关键词深度分析流程.md` | 竞品关键词深度分析 |
| `wiki/技术配置/GitHub高星标学习笔记.md` | GitHub高星标内容学习 |

**移动任何 wiki 文件前**，必须先用 `openclaw cron list --json` 导出任务，grep 全部 prompt 确认无路径依赖。

### R3. 索引层组织优先于物理移动
当某个目录"文件太多显得碎"时，**优先在索引里做逻辑分组**（如案例库按周、SOP 按类型），而不是移动文件。
物理移动只在收益明显且不触碰 R2 时执行。

### R4. 链接规范
- 优先用带路径 wikilink：`[[目录/文件]]`
- 表格内别名需转义：`[[目录/文件\|别名]]`；**表格外不要转义**（会变 `[[路径\]]` 死链）
- 跨 vault 引用（wiki → memory）改用 GitHub 绝对 URL

### R5. 写入前查重
新结论写入前先读 `wiki/行业知识/结论索引.md`（含分册目录）检查矛盾，避免重复结论。

### R6. 结构变更必须同步脚本数据源（2026-09-12 事故）

移动 / 拆分 / 重命名知识库文件时，**必须同步检查并更新读取它们的脚本**——否则脚本会**静默**读到不完整数据（无报错、正常退出），长期无人察觉。

**事故实例**：结论索引从单文件拆为「索引层 + 20 分册」后，`scripts/evolution_engine.py` 仍只读 `结论索引.md` 单文件 → **漏读 95.4% 的结论**（77 / 1668 条），验证引擎连续数周"无事可做"。

**检查清单**：

1. **找脚本**：`grep -rln "<旧路径或文件名>" scripts/`
2. **看写法**：
   - `WIKI_DIR.glob("**/*.md")` 递归扫描 → ✅ 安全（如 `llmwiki_query.py`）
   - 硬编码单文件路径 → ⚠️ 必须更新（如 `CONCL = "…/结论索引.md"`）
3. **实测对比**：修复前后输出的条数 / 字段应有明显差异（本例 64 → 1152 条）

**同样适用于**：任务 prompt 里的路径（见 R2）、cron 的 `--command` 参数、数据源 glob 规则。

### R7. 验证类脚本必须接入最新权威数据源

数据源会滞后：`evolution_engine.py` 原先只读 ontology db（最新 2026-08-19），而 SSOT CSV 已到 2026-09-06 —— **用 3 周前的数据"验证"今天的结论**，验证结果不可信。

**规则**：凡用于"验证/裁决/对比"的脚本，必须显式接入最新权威数据源（客流 → SSOT CSV；指数 → ontology db），并在输出中标注各数据源的截止日期，便于判断新鲜度。

## 页面类型

### 1. 档案页 (Archival)
- 用途：记录静态信息、历史数据
- 命名：`<主体>基础档案.md`
- 示例：`电影小镇基础档案.md`
- 特点：长期有效，定期更新

### 2. 分析页 (Analysis)
- 用途：深度分析、洞察、趋势
- 命名：`<主体><主题>分析.md`
- 示例：`清明上河园深度分析.md`
- 特点：带时间戳，追踪变化

### 3. 方法页 (Method)
- 用途：SOP、操作流程、最佳实践
- 命名：`<主题>方法.md`
- 示例：`小红书运营方法.md`
- 特点：可执行、有步骤

### 4. 记录页 (Log)
- 用途：时间序列记录、操作日志
- 命名：`YYYY-MM-DD-<事件>.md`
- 示例：`2026-04-15-日报整合.md`

## Ingest 规则（新知识入库）

当有新的 raw 文件时，LLM 必须：

1. **读取 raw** - 原始资料放在 `raw/` 对应分类下
2. **写摘要** - 100字以内提炼核心信息
3. **更新实体页** - 创建或更新 `wiki/<分类>/` 下的页面
4. **维护索引** - 更新 `index.md` 中的对应条目
5. **记录日志** - 在 `log.md` 中追加操作记录

**级联规则**：一个来源可能更新 3-10 个页面

## 命名规范

- 使用中文标题
- 文件名用英文：`wiki/景区运营/cinema-town-basic.md`
- 链接用中文：`[[电影小镇/基础档案|电影小镇基础档案]]`
- 时间格式：`YYYY-MM-DD`

## Lint 检查规则

每月执行一次 lint 检查，查找：

| 问题类型 | 检查方法 | 处理方式 |
|---------|---------|---------|
| 矛盾点 | 全文搜索冲突关键词 | 标记并提出合并建议 |
| 过时信息 | 检查超过30天未更新的档案页 | 提醒更新 |
| 孤儿页面 | index.md 中未引用的页面 | 删除或补充索引 |
| 缺失概念 | 检查是否有遗漏的重要主题 | 提出新建建议 |

---

## Query 规则（查询）

- 优先读 wiki 页面，不是 raw 文件
- wiki 页面答案可存回 wiki 成为新页面
- 探索结果必须沉淀，不能只留在聊天记录

---

## 更新频率

| 页面类型 | 更新时机 |
|---------|---------|
| 档案页 | 数据有变化时 |
| 分析页 | 每周竞品分析后 |
| 方法页 | 有新 SOP 时 |
| 索引页 | 任何页面变更后 |
| 日志页 | 每次操作后追加 |
